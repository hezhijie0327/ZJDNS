### F1 [HIGH] race — Shutdown iterates listener slices without listenerMu while Start goroutines append under it
- **文件**: server/protocol/tls/server.go:338
- **问题**: Start() launches per-protocol goroutines (server.go:205-257) that call startDOTServer/startDOHServer/startDOQServer/startDOH3Server/startDTLSServer; every one appends to s.dotListeners/s.doqConns/s.httpsListeners/s.dohServers/s.h3Listeners/etc. under s.listenerMu (e.g. tls.go:41-43, https.go:52-54, quic.go:56-58, http3.go:38-40, dtls.go:60-62). Shutdown() (server.go:333-402) iterates all of those slices and reads s.h3Server (line 358) with NO lock. The signal handler is armed in server.New() (server/tasks.go:22,166-184) before Start is ever invoked, so a SIGINT/SIGTERM arriving during listener startup runs shutdownServer() -> s.tls.Shutdown() concurrently with the append goroutines. Note closeListeners() (line 291-329) DOES take listenerMu, so the two close paths use different locking discipline on the same fields. Appends happen under listenerMu while Shutdown reads without it — a confirmed data race on the slice headers.
- **风险**: Data race on slice headers during shutdown-during-startup: torn iteration can miss listeners (bound ports leak until process exit) or, under the race detector / concurrent append growth, corrupt the slice and crash. Violates the codebase's own locking discipline (closeListeners takes the lock, Shutdown does not).
- **修复建议**: Take s.listenerMu around the slice iterations and the s.h3Server read in Shutdown() (or factor the close loop into closeListeners and call it from Shutdown under the lock).

### F2 [HIGH] race — Shutdown iterates listener/HTTP-server slices with no synchronization at all; Start appends are unsynchronized
- **文件**: server/protocol/tlcp/server.go:201
- **问题**: tlcp.Start() (server.go:168-193) calls startDOTServer (appends s.dotListeners at tlcp.go:53), startDOHServer (appends s.dohListeners/s.dohServers at http_tlcp.go:36,45) and startDTLCPServer (appends s.dtlcpListeners at dtlcp.go:236) — plain `append` with no mutex. Shutdown() (server.go:196-228) iterates all four slices without any lock. The signal handler is armed in server.New() (server/tasks.go:22) before the server starts, and tlcp.Start runs inside a goroutine (server/server.go:447-456), so a SIGINT during TLCP startup makes Shutdown iterate the slices concurrently with appends.
- **风险**: Concurrent append + iteration on the same slice header is a data race: can silently skip listeners (shutdown hangs or ports stay bound) or corrupt memory. Unlike the TLS package, tlcp has no mutex at all for these fields.
- **修复建议**: Add a sync.Mutex protecting the four listener/server slices, take it in both the Start append sites and Shutdown, and also protect s.handler (written in Start, read by serveDOH/handleDOTConn).

### F3 [MEDIUM] resource — DTLS accept-error loop has no backoff sleep — spins at 100% CPU on sustained temporary errors
- **文件**: server/protocol/tls/dtls.go:90
- **问题**: handleDTLSConnections (dtls.go:84-97): on Accept error it checks ctx, then `continue`s directly — no time.Sleep. Every other accept loop in the protocol packages backs off: tls.go:70 and quic.go:102 sleep DefaultAcceptRetryDelay, dtlcp.go:268-280 sleeps 50ms with an explicit comment ('an immediately-repeating temporary failure (e.g. EMFILE) would otherwise spin the accept loop at 100% CPU'), tlcp.go:79 and dnscrypt/tcp.go:74 sleep too. A sustained temporary accept error (EMFILE, ENOBUFS) makes the DTLS accept loop busy-spin at 100% CPU.
- **风险**: 100% CPU burn and log flooding on any sustained temporary accept error (EMFILE under fd exhaustion, etc.), degrading the whole server exactly in the failure scenario where it should be recovering.
- **修复建议**: Add a select-with-timer backoff identical to dtlcp.go:268-280 (or reuse config.DefaultAcceptRetryDelay) before the `continue` in the DTLS accept error path.

### F4 [MEDIUM] resource — TLCP DoT handshake is bounded only by the 60s idle timeout — idle-connection flood starves the shared serverGroup
- **文件**: server/protocol/tlcp/tlcp.go:93
- **问题**: handleDOTConn (tlcp.go:86-108) sets SetReadDeadline(now + config.DefaultTCPPoolIdleTimeout) (60s) before the first ReadTCPMsg, so the lazy TLCP handshake is bounded by 60s. The TLS package fixed exactly this hazard for DoT: tls.go:76-81 sets DefaultTLSHandshakeTimeout (10s) before the first read, with a comment explaining that a flood of never-handshaking connections otherwise holds a shared errgroup slot for the full idle timeout, starving the other listeners. TLCP shares one serverGroup (SetLimit config.DefaultServerGoroutineLimit=1024) across DoT-TLCP, DoH-TLCP and DTLCP accept loops — a flood of idle TLCP TCP connects occupies slots 6x longer than the TLS design allows and blocks DTLCP/DoH accept-loop serverGroup.Go calls.
- **风险**: Resource exhaustion: an attacker opening TLCP TCP connections without handshaking can starve the DTLCP and DoH-TLCP listeners (their accept loops block on serverGroup.Go once the 1024-slot limit is hit) for up to 60s per connection.
- **修复建议**: Mirror the tls package: set a short pre-handshake deadline (config.DefaultTLSHandshakeTimeout) before the first ReadTCPMsg and extend to DefaultTCPPoolIdleTimeout after the first successful read.

### F5 [MEDIUM] resource — TLCP DoT response writes have no write deadline — a stalled peer blocks the connection goroutine indefinitely
- **文件**: server/protocol/tlcp/tlcp.go:119
- **问题**: sendDOTResponse (tlcp.go:113-124) calls zdnsutil.WriteTCPMsg(conn, resp) (tcpframe.go:100-115) which does a plain conn.Write with no SetWriteDeadline; handleDOTConn only ever sets READ deadlines (line 93). Every other writer in the protocol packages sets a write deadline: tls.go:124 (DefaultDNSQueryTimeout), dtlcp.go:368 (DefaultDTLSIdleTimeout, same package), dnscrypt/tcp.go:42 (defaultWriteTimeout). A client that keeps its TCP connection alive but stops reading (full receive window) leaves the handler goroutine blocked in Write forever — the 60s read deadline does not cover the write direction, and a live peer ACKs keepalives so TCP never tears the connection down.
- **风险**: Unbounded goroutine + fd leak per malicious connection (up to serverGroup limit 1024), and after the limit is hit the TLCP accept loops block entirely. DNSCrypt's TCP path comments exactly this hazard ('A client that stops reading must not block this goroutine forever').
- **修复建议**: Set conn.SetWriteDeadline(time.Now().Add(config.DefaultDNSQueryTimeout)) before WriteTCPMsg in sendDOTResponse (or inside the loop before each write).

### F6 [LOW] magic-number — Hard-coded 50ms accept-error backoff instead of config.DefaultAcceptRetryDelay
- **文件**: server/protocol/tlcp/dtlcp.go:268
- **问题**: handleDTLCPConnections (dtlcp.go:264-281) declares `backoff := 50 * time.Millisecond` inline on the error path. config.DefaultAcceptRetryDelay (config/defaults.go:135, 100ms) exists for exactly this purpose and is used by the DoT/DoQ/DNSCrypt accept loops. A second, differently-valued retry delay for the same concept is a magic number that will drift from the documented default.
- **风险**: Inconsistent backoff policy across accept loops; a future change to DefaultAcceptRetryDelay (e.g. under load tests) silently misses DTLCP.
- **修复建议**: Replace the inline 50ms with config.DefaultAcceptRetryDelay (or a named const in this package if a different value is truly required, with a comment).

### F7 [LOW] dead-code — signSerial.Set(signSerial) / encSerial.Set(encSerial) are self-aliasing no-ops
- **文件**: server/protocol/tlcp/certs.go:89
- **问题**: certs.go:89 `signSerial.Set(signSerial)` and certs.go:98 `encSerial.Set(encSerial)` pass the receiver as the argument. big.Int.Set returns immediately when z == x (`if z != x { ... }`), so both calls are no-ops — dead code that looks like a copy/paste artifact of the CA-serial cloning pattern (caSerial is cloned via rand.Int, but sign/enc serials are already fresh rand.Int values).
- **风险**: Misleading code: a reader assumes the serials are being copied/cloned; the two calls do nothing and can be deleted without behavioral change.
- **修复建议**: Delete both self-Set calls (or replace with a comment if the intent was to clone, e.g. `signSerial = new(big.Int).Set(signSerial)`).

### F8 [HIGH] unbounded-growth — tcpWriteEntry.refs never returns to 0 — tcpWriteMu sweep is dead code, per-connection map grows unboundedly
- **文件**: server/bridge.go:65
- **问题**: In handleDNSRequest, refs accounting is: new entry +1 at line 56 (placeholder, only released on the type-mismatch path line 60), +1 at line 65 when the entry was already present (loaded), +1 at line 76 (per-request in-flight), and a single -1 at line 81 (SERVFAIL path) or line 121 (goroutine exit). Per request on an existing entry this nets +1 (65+76-1); on the creating request it also nets +1 (56+76-1). There is no compensating decrement releasing the placeholder/line-65 increment after the line-76 in-flight ref is registered, so after the first request completes refs >= 1 forever. The sweep in server/tasks.go:132 (`if entry.refs.Load() != 0 { return true }`) therefore can never delete any entry that ever served a request, and the only other cleanup (lastAccess < cutoff at tasks.go:135) is gated behind the same refs==0 check. s.tcpWriteMu (sync.Map, server.go:59) is keyed by `w.RemoteAddr().String()` = "ip:port", i.e. one entry per TCP connection ever made, each holding a writeMu channel + capacity channel + entry struct — the map grows without bound for the lifetime of the process.
- **风险**: Unbounded memory growth: every TCP connection ever accepted adds a permanent map entry (each with two channels); on a busy public server with NAT'd clients reconnecting on new ports this accumulates thousands of entries per hour, permanently. The designed eviction (startTCPWriteMuSweep) is silently dead.
- **修复建议**: Release the placeholder ref after the in-flight ref is registered: after line 76 add `newEntry.refs.Add(-1)` (or restructure so exactly one ref per request is held: remove the line-65 Add and decrement the placeholder on all success paths). Then refs returns to 0 when idle and the sweep deletes stale entries again. Add a unit test asserting refs==0 after a completed request.

### F9 [HIGH] data-race — Client.Close writes c.proxyDialers = nil unsynchronized while the query hot path reads it — shutdown-window data race
- **文件**: server/upstream/client.go:306
- **问题**: upstream.Client.Close() (client.go:299-307) does `c.proxyDialers.Range(...)` then `c.proxyDialers = nil` with no lock, while the query path calls proxyDialer() (server/upstream/warmup.go:22-50) which reads c.proxyDialers unsynchronized (`c.proxyDialers == nil` at line 27, `.Get(server.Proxy)` at line 31, `.Set(...)` at line 48). These can run concurrently during shutdown: plain-TCP handler goroutines are fire-and-forget (bridge.go:117-119 documents "No WaitGroup is needed") and plain/server.go Shutdown only closes listeners (dns.Server.Shutdown does not wait for in-flight handlers), so an in-flight query can still be mid-ExecuteQuery when queryClient.Close() runs after the background wait in server/tasks.go:289-291. Note the sibling tls.Client.Close (server/upstream/tls/client.go:106-108) explicitly documents that nil'ing its LRU maps would race in-flight queries and deliberately does NOT do it — this site is inconsistent with that established pattern.
- **风险**: Race-detector trip during every shutdown that has in-flight proxied queries; a reader observing the nil can panic in lrumap.Map.Get/Set (m.mu.Lock on nil receiver), recovered by HandlePanic → dropped query/SERVFAIL at shutdown, or silently return nil dialer → query routed without the proxy (wrong egress path for proxied upstreams).
- **修复建议**: Follow the tls.Client pattern: drop the `c.proxyDialers = nil` write entirely (the map dies with the Client; dialers were already closed by the Range above), or guard the field with a mutex in proxyDialer and Close.

### F10 [LOW] lock-drop — Exchange returns from inside the c.mu critical section without unlocking
- **文件**: server/upstream/pool/tcp.go:157
- **问题**: In Conn.Exchange, c.mu is locked at line 140; the trackingID-collision branch at lines 149-161 contains `if len(writeBuf) < zdnsutil.DNSFramePrefixLen+2 { return nil, ... }` (lines 157-159) which returns WITHOUT c.mu.Unlock() (the unlock is only at line 170). The branch is currently unreachable — writeBuf is sized DNSFramePrefixLen+len(msgData) and a packed DNS message always has >= 12 header bytes, so len(writeBuf) >= 14 > 4 — but it is a success-path-unlock defect: if the invariant ever changes (e.g. a zero-copy packer emitting a short/empty body), the connection's mutex stays locked forever, deadlocking every subsequent Exchange on that Conn and readLoop's inflight delivery.
- **风险**: Latent permanent deadlock of a pooled pipelined connection (and all queries routed to it) if the defensive branch is ever reached; today it is only a correctness smell that fails static analysis expectations.
- **修复建议**: Restructure so the lock cannot be dropped: move the collision loop and bounds check before c.mu.Lock() (the check only reads writeBuf, which is not modified under the lock), or use a helper with explicit `c.mu.Unlock()` before the return.

### F11 [LOW] lock-discipline — zone.Evaluator.dynamics/bypass maps written without synchronization in LoadRules, read on the query hot path
- **文件**: zone/zone.go:120
- **问题**: LoadRules writes `e.dynamics = make(map[string]*dynamicEntry)` (line 120) and `e.bypass = bypass` (line 144) with no mutex, while Evaluate reads them on the query path: `for i, tags := range e.bypass` (line 261) and `if de, ok := e.dynamics[qname]` (line 277). Today LoadRules is only invoked at server startup (server/server.go:165) before any listener starts, so there is no live race; but the sibling fields loadedAt/ruleCount use atomics (lines 67-68) precisely for concurrent access, and nothing in the Evaluator prevents a future runtime reload call site (config watch, ZJDNS dynamic-reload rule) from silently creating a map data race on the hot path — the current code offers no synchronization to discover.
- **风险**: Latent data race: any future runtime LoadRules call while queries are in flight will corrupt the dynamics/bypass maps (concurrent map read/write panic or torn rule state) with no obvious failing test.
- **修复建议**: Guard dynamics and bypass with a sync.RWMutex (RLock in Evaluate, Lock in LoadRules), or document a hard invariant that LoadRules is init-only and add a defensive comment at both write sites; prefer the mutex since the file already uses atomics for the other hot-path fields.

### F12 [MEDIUM] rfc-compliance — EDNS VERSION never inspected — no BADVERS response per RFC 6891 §6.1.3 MUST
- **文件**: edns/edns.go:102
- **问题**: RFC 6891 §6.1.3 (archived, line 466-469): 'If a responder does not implement the VERSION level of the request, then it MUST respond with RCODE=BADVERS.' ZJDNS never reads the request OPT's VERSION field: middleware/edns.go:32-39 forces a full unpack and inspects only Pseudo options (ECS/Cookie/Padding); no code anywhere reads the OPT TTL bits 16-23 (grep for Ttl>>16 / Version() / RcodeBadVers across server/ and edns/ finds nothing — the only RcodeBad* matches are RcodeBadCookie=23, a different code). The response OPT is synthesized by ApplyToMessage (edns/edns.go:94-107), which sets msg.UDPSize and msg.Security only; miekg/dns v0.6.87 (dns.go:196) states 'Version is the EDNS version, always zero'. A client sending an EDNS query with VERSION=1 therefore receives a normal version-0 response instead of the mandated BADVERS(16).
- **风险**: Protocol non-compliance on an RFC MUST; EDNS-version probing tools (e.g. edns-version checks) and future EDNS versions will misidentify the server as supporting VERSION>0, and the server will silently process queries under an unsupported version contract.
- **修复建议**: In the EDNS middleware after full unpack, read the request OPT version (opt.Hdr.TTL >> 16 & 0xFF via the OPT.Version() accessor in miekg/dns v0.6.87) and, if nonzero, reply RCODE=BADVERS with an OPT carrying the server's version (0) instead of delegating into the chain.

### F14 [LOW] rfc-compliance — Malformed cookie lengths 9-15 and >40 get BADCOOKIE instead of the RFC 7873 §5.2.2 FORMERR
- **文件**: server/handler/middleware/edns.go:84
- **问题**: RFC 7873 §5.2.2 (archived, lines ~390-400): cookie total lengths 9-15 ('shorter than the minimum COOKIE option with both a Client Cookie and a Server Cookie (16 bytes)') and >40 ('longer than the maximum valid COOKIE option (40 bytes)') MUST produce FORMERR; valid lengths are exactly 8 and 16-40. The code path: ParseCookie (edns/cookie.go:277-301) accepts any length >= 8 and strips the first 8 bytes as client cookie; middleware/edns.go:84-89 then returns BADCOOKIE whenever the remaining server-cookie length is nonzero and != 16 — so totals 9-15 (server portion 1-7) and >40 (server portion >32) produce BADCOOKIE(23), never FORMERR. Also, the FORMERR comment cites 'RFC 7873 §5.3' (middleware/edns.go:72 and cookie.go:275), but §5.3 is 'Processing Responses' (client-side); the malformed-length rule is §5.2.2.
- **风险**: Slightly wrong error code to clients with pathological cookies; RFC 7873 §5.2.2's FORMERR semantics (reject the request) are replaced with a BADCOOKIE that the client may retry pointlessly, and the wrong §5.3 citation misleads maintainers.
- **修复建议**: Classify by total cookie length: <8 or 9-15 or >40 -> FORMERR; 17-40 (invalid server cookie) -> BADCOOKIE per §5.2.4/§5.2.2; fix the two §5.3 comments to §5.2.2.
